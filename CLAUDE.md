# crypto-trading-lab

Личная лаборатория торговых гипотез: собирает данные, кодирует стратегии, меряет их
на истории и вперёд, и по замеру двигает по ступеням от бэктеста к реальным деньгам.
Один пользователь-оператор, Telegram и веб-экран — интерфейс.

## Работа на сервере: три правила, каждое стоило времени

1. **Долгие задачи запускать отвязанно от ssh.** Сессия рвётся на многоминутных операциях
   («Connection reset by peer»), и в переднем плане вместе с ней умирает всё — так оборвались
   пересборка образа и часовой замер. Сервер при этом здоров: OOM-убийств нет, контейнеры
   живы. Готовый рецепт — `scripts/run-detached.sh <имя> "<команда>"`, ожидание —
   `run-detached.sh --wait <имя>`. **Вывод задачи попадает в лог целиком**, поэтому если она
   могла напечатать секрет (упавший assert с `DATABASE_URL` — реальный случай), лог удалять
   через `shred -u`.
2. **Перед сбором данных сверять версию кода в образе.** Починка в слое данных бесполезна,
   пока контейнер старый: дефект имени срочного контракта был исправлен, но сборщик пошёл
   на прежнем образе, и 48 «квартальных» рядов оказались копиями бессрочного. Проверка —
   `docker compose … exec worker printenv LAB_CODE_VERSION` против `git rev-parse HEAD`.
3. **Не пересобирать, пока внутри идёт замер.** `up -d --build` пересоздаёт контейнер и
   убивает расчёт без следа. Перед пересборкой — `docker top crypto-trading-lab-worker-1`.

**Тесты на сервере гоняются в ОДНОРАЗОВОМ контейнере**: в боевом образе нет ни dev-зависимостей
(`UV_NO_SYNC=1`), ни каталога `tests`. Рабочий вызов:

```bash
docker compose -f deploy/docker-compose.yml run --rm --no-deps \
  -v /opt/crypto-trading-lab:/src -w /src \
  -e UV_NO_SYNC=0 -e UV_PROJECT_ENVIRONMENT=/tmp/venv-test \
  --entrypoint sh worker -c "uv sync --group dev -q && uv run pytest -q; uv run ruff check ."
```

Монтировать надо весь репозиторий, а не только `tests`: иначе четыре теста падают
на отсутствии `.env.example`, `alembic.ini`, `candidates/` и `scripts/`.

## Главные понятия

- **Ветка** (`Branch`) — рынок со своими лимитами и порогом: `cex-spot`, `cex-perp`,
  `dex-perp`, `copy`, `meme`, `nft`, `prediction`, `rh`. Группы веток и доли капитала —
  `config/limits.yaml`.
- **Стратегия** — правило: `StrategyManifest` (ветка, площадка, инструменты, `params`,
  `can_backtest`, `stop`, `ttl_s` внутри `params`) плюс `on_bar/on_event -> [Signal]`.
  Id — `<ветка>-<источник>-<слаг>`. Два реестра, не путать: `strategies.registry` — какие
  правила умеет собирать код; `core.registry` — записи со ступенью и статусом в базе.
- **Ступень** (`Rung`): `backtest → paper → micro → signal → semi → auto`. Ниже `micro`
  реальных ордеров нет. `semi → auto` — только рукой оператора (`OperatorRequired`).
- **Статус** (`Status`): `candidate · measuring · passed · failed · degraded · retired`.
  `degraded` разрешает закрывать позиции и запрещает открывать.
- **Замер** (`core.measure.run`) — `Measurement` со снимком метрик, `data_hash`,
  `code_version`, `costs_version`. Режимы: `backtest`, `paper`, `micro`, `forward`.
  Нечего посчитать — `status="incomplete"` с причиной, а не выдуманное число.
- **Порог** (`config/threshold.yaml`) — правило прохождения ступени: ≥30 сделок,
  EV после издержек > 0, MaxDD в лимите ветки, лучше бенчмарка (BTC buy-and-hold).
  Результат — `passed | failed | insufficient`.
- **Издержки** (`core.costs`) — комиссия, проскальзывание, фандинг, газ, роялти;
  считаются и в бумаге, и по факту филла. Замера без издержек не бывает.

## Правила, которые легко нарушить

1. **Ни один ордер не уходит на площадку без `core.risk.check(...) == Allow`.** Путь
   один — `ops.worker.place_signal`. Обёртка `ops.stop_watch.StopWatch.guard` при
   `Deny(strategy_stop_*)` на открывающем ордере переводит стратегию в `degraded`;
   на закрывающем (`reduce_only`) это дефект ядра (`RiskCoreError`), а не отказ —
   закрыть позицию можно всегда.
2. **Решение стратегии пишется в журнал ДО исхода** — `Journal.record_signal` с
   `decided_at` и `inputs_hash`; исход дописывается потом (`set_outcome`). То же в
   `feeds.social.journal` для чужих публичных сигналов.
3. **Деньги — `Decimal`, не float.** Валюта учёта — USD. Время в базе UTC, показ — `Europe/Samara`.
4. **Секреты — только через `.env` по именам из `.env.example`.** Ни ключа в коде, тестах
   или логах; логируется «заполнено / пусто». Ключ с правом вывода средств отклоняется
   при старте (`KeyRejected`).
5. **Тесты не ходят в сеть.** Живые API — за `LAB_LIVE_TESTS=1` (без него 29 тестов
   пропускаются). `tests/conftest.py` ставит `LAB_CEX_TRANSPORT=fake`. Всё внешнее —
   за интерфейсом, в тестах фейк: `FakeTransport`, `FakeHttpTransport`, `FakeRhTransport`,
   `FakeNftMarket`, `FakeExecutor`, `FakeMintClient`.
6. **Режим `paper`/`live` — по экземпляру исполнителя, не смешивать.** У paper-экземпляра
   `positions/fills/balance` считаются в памяти, у live — берутся с площадки; `place` с
   чужим режимом бросает ошибку. Worker держит по экземпляру на режим.
7. **Новый исполнитель регистрируется в `lab.executors.registry`** (в `__init__.py` своего
   пакета, фабрика без аргументов → paper). Контрактный тест
   `tests/contracts/test_executor_contract.py` параметризован по `registry.all()` и
   подхватит его сам. Сейчас там 17 имён (`bybit okx binance hyperliquid jupiter uniswap
   pancake stonfi opensea magiceden tensor zora nft_mint_solana nft_mint_evm polymarket
   robinhood fake`).
8. **Стратегии не импортируют `core.ladder`, `core.risk`, `core.registry`, `executors`** —
   это проверяет `tests/strategies/test_base.py`.
9. **Миграции — только новой ревизией**, голова одна (`0011`). Правка уже выданной ревизии —
   нет; `alembic heads` должен показывать ровно одну строку.

## Окружение

Минимум, чтобы что-то заработало:

- **`DATABASE_URL`** — без него всё, что трогает базу (`lab strategy/candidate/measure/ops/service`),
  падает с `DatabaseUrlMissing`. `lab venues` и `alembic` живут без него: alembic берёт
  запасной URL из `alembic.ini`. Начинать с `cp .env.example .env` — файл копируется
  как есть и даёт рабочую конфигурацию без ключей (все площадки «только данные»).
- **Postgres 16** локально, роль `lab`/`lab`, базы `lab` и `lab_test`. Тесты берут
  `TEST_DATABASE_URL` (по умолчанию `postgresql+psycopg://lab:lab@localhost:5432/lab_test`);
  базы нет — весь набор `skip`, а не падение.
- `TELEGRAM_BOT_TOKEN` + `TELEGRAM_ADMIN_ID` — без них `lab service bot` печатает, что не
  заданы, и живёт одним heartbeat'ом.
- `WEB_USER`/`WEB_PASSWORD` — без них `lab service web` печатает разовый пароль в лог
  (веб без авторизации не поднимается вообще).
- Ключи площадок — без них ветка честно уходит в «только замер» / «только данные»
  (`BranchMode`, `check_trading_access`), а не притворяется рабочей.
- `CHAINS_ENABLED` — какие сети включены и в каком порядке; неизвестное имя → `ConfigError`.
- `REAL_CAPITAL_CAP`, `BUDGET_MONTH_USD`, `BACKUP_DIR`, `LAB_DATA_ROOT` (по умолчанию `data/`) —
  поверх yaml.

## Грабли

- **Хвостовой комментарий в `.env` доезжает до контейнера как ЗНАЧЕНИЕ.** Свой парсер
  `lab.config.env.load_dotenv` его срезает (вне кавычек), поэтому с хоста всё выглядело
  правильно. Но в compose `.env` идёт через `env_file`, а тот ничего не срезает: строка
  `BYBIT_API_KEY=   # ключ Bybit` кладёт в переменную текст комментария. На сервере так
  «заполнились» 26 ключей, и `lab venues` рапортовал «подключена» по всем площадкам вместо
  честного «только данные» — система считала, что у неё есть ключи всех бирж. Поэтому в
  `.env.example` пояснения стоят ОТДЕЛЬНЫМИ строками над ключом; хвостовые не возвращать.
  Проверка на сервере: `docker compose … exec worker uv run python -m lab venues` — без
  ключей все площадки должны быть «только данные». Не подключать `python-dotenv`: он делает
  это иначе.
- **`migrations/env.py` и `DATABASE_URL` при тестах.** Порядок в `db.engine.alembic_url`:
  `attributes["sqlalchemy.url"]` (программный вызов) → `DATABASE_URL` → `.env` →
  `alembic.ini`. Программный вызов сильнее окружения намеренно: иначе миграции тестов
  уезжают на боевую базу. `tests/conftest.py` на это опирается — не «упрощать».
- **Postgres в песочнице сам не поднимается.** `pg_ctlcluster 16 main start`, проверить
  `pg_lsclusters` (должно быть `online`, порт 5432).
- **Сети к биржам в песочнице нет.** `lab ops status` показывает все площадки
  `недоступна`, Polymarket — `гео-блок (403 Forbidden)`. Это ожидаемо: `lab data backfill`
  и всё живое здесь не проверить. Отказ источника — деградация (`FeedUnavailable` →
  замер `incomplete`), процесс не падает.
- **Живая подпись транзакций не реализована.** `solders`/`web3`/TON-SDK/`py-clob-client`
  в дерево зависимостей не втянуты (тяжёлые, для чтения не нужны). Клиенты грузят их
  лениво и в `live` бросают `TradingUnavailable` с текстом, чего не хватает, — ветка
  уходит в «только замер», а не молчит. Касается `executors.dex`, `executors.nft` (минт),
  `executors.polymarket`.
- **Docker-демона здесь нет** — проверяется только `docker compose ... config`, `up` не
  запускается. Сервисы отлаживать через `lab service <s> --once`.
- **Compose читает `.env` рядом с собой, то есть `deploy/.env`, а не корневой.** Подстановки
  `${WEB_BIND}`, `${DB_BIND}`, `${POSTGRES_PASSWORD}` без ссылки `deploy/.env → ../.env`
  молча уезжают в умолчания: веб встаёт на `127.0.0.1:8080`, пароль базы становится `lab`.
  Отказ тихий — `up` проходит, просто не тот порт. Ссылку делает `deploy/setup.sh`; проверка —
  `docker compose -f deploy/docker-compose.yml config | grep published`. На env_file внутри
  сервисов это не влияет: в контейнеры `../.env` попадает и без ссылки.
- **`DATABASE_URL` в `.env` — адрес для запуска с ХОСТА (`localhost:5432`), в compose он не
  подставляется.** В `docker-compose.yml` хост базы зашит как `db`. Пока `.env` был не виден
  compose, это держалось само собой; со ссылкой (грабля выше) значение из файла едва не уехало
  в контейнеры — `migrate` падал на `connection to 127.0.0.1:5432 refused`. Не «упрощать»
  обратно в `${DATABASE_URL:-…}`.
- **`WEB_BIND` значит два разных адреса.** В `.env` это адрес **на хосте** (строка `ports`),
  а `lab.web.bind_address` читает ту же переменную и решает, что слушать **внутри**
  контейнера. Совпадение смыслов ломало веб: приложение садилось на loopback контейнера,
  куда docker-proxy не ходит, и опубликованный порт отвечал отказом при `healthy` сервисе
  (heartbeat живёт независимо от сокета). Поэтому в compose сервису `web` жёстко задан
  `WEB_BIND: 0.0.0.0:8080`. Наружу это ничего не открывает: публикуется только
  `127.0.0.1:<порт>` хоста.
- **`docs/` — часть рантайма, а не только документация.** `lab.strategies.presets.cards`
  читает карточки из `docs/research/strategies/` при импорте реестра, поэтому каталог
  обязан быть в образе (`COPY docs ./docs`). Без него в контейнере падает всё, что собирает
  стратегии — `measure`, worker, discovery — с `FileNotFoundError`, при этом тесты
  из репозитория проходят: там `docs/` на месте. Переносить карточки в `config/` или
  в пакет — можно, но тогда править `CARDS_DIR` и путь в 31 карточке.
- **Стоп стратегии в бэктесте применяется, лимиты ветки — нет.** `simulate` считает пробой
  теми же формулами, что живое риск-ядро (просадка по кривой закрытых сделок от капитала,
  дневной — сумма `pnl_net` за сутки), и после пробоя ведёт себя как `degraded`: закрывающие
  сигналы проходят, открывающие отсекаются. Факт срабатывания — в снимке (`stopped_at`,
  `stop_rule`, `blocked_signals`), `measure show` печатает строку. **Чего в симуляции всё ещё
  нет:** лимитов ветки (`branch_stop`, `branch_share`), потолка плеча и `real_capital_cap` —
  они стоят на пути живого ордера (`ops.worker.place_signal`, `StopWatch`).
  Цена ошибки видна на числах: без стопа `cex-perp-preset-trailing-breakout-bot` показывал
  −222.8% при просадке 223% (больше капитала), со стопом — −24.3%.
- **`run-detached.sh <имя> "bash /root/<имя>.sh"` — форк-бомба.** Обёртка пишется ровно
  в этот файл, поэтому команда, ссылающаяся на него, заставляет скрипт вызвать сам себя.
  10.09.2026 такой вызов за минуту поднял нагрузку до 292, съел всю память и уронил по OOM
  **четыре контейнера, включая боевого бота соседнего проекта**. Отказ был тихий и
  правдоподобный: в логе копились строки «ГОТОВО код=0», как будто задача отработала.
  Теперь скрипт такой вызов отклоняет. Если рекурсия всё же случилась: сначала
  `rm -f /root/<имя>.sh` (без файла новые вызовы падают), потом `pkill -9 -f <имя>` —
  в обратном порядке процессы плодятся быстрее, чем их убиваешь. Дальше поднять соседей:
  `docker start crypto-trader-bot-1 wake-collector beach-volley-coach`.
- **`candidate` система не видит вовсе.** Воскресное переизмерение берёт только
  `measuring` и `passed`. Стратегию ставит на лестницу поиск кандидатов, кнопка в боте
  или `lab strategy start <id>` — заведённая сценарием так и лежит в реестре, пока её
  не возьмут в работу. Первый честный прогон цикла ответил «измерено 0» и был прав.
- **Окно переизмерения зависит от таймфрейма** (`remeasure.window_days_by_tf`): порог
  требует 30 сделок, а дневное правило за квартал их не наберёт физически. Кэш-энд-керри
  делает 48 сделок за 5.5 лет — на 90 сутках вечный `insufficient`, и медленная стратегия
  не могла пройти лестницу в принципе.
- **DuckDB забирает 80% памяти КОНТЕЙНЕРА и убивает замер молча.** При `mem_limit: 1200m`
  движок запроса ставит себе 960 МБ — не оставляя ничего ни рабочему процессу, ни самому
  Python. Три замера минутных стратегий подряд получили SIGKILL от cgroup ровно на 946 МБ,
  и **каждый завершился без единой строки вывода**: снаружи это неотличимо от «замер
  ничего не сказал». Теперь `CandleStore` ставит 256 МБ и 2 потока (`LAB_DUCKDB_MEMORY`,
  `LAB_DUCKDB_THREADS`). Проверка при пустом выводе — та же, что и раньше:
  `dmesg -T | grep -i "killed process"`, плюс `docker inspect … --format "{{.State.OOMKilled}}"`.
- **Режим маржи решает судьбу хеджа: `isolated` против `cross`.** Параметр карточки
  `margin_mode`, по умолчанию `isolated` — так на бирже и стоит, пока не переключишь.
  Один и тот же код кэш-энд-керри даёт −2.38% и смерть счёта на изолированной марже и
  +4.41% с пройденным порогом на кросс-марже: 08.05.2021 фьючерс потерял 103% залога,
  а спот в тот же момент был +114% от входа. **Сокращать позицию бесполезно** — залог
  пропорционален размеру, цена ликвидации не сдвигается. Чего модель не знает: ступеней
  плеча, дисконтов на обеспечение и того, что цены остальных ног берутся последние
  известные (бары приходят по одному).
- **Фандинг доступен ЛЮБОЙ стратегии, где в списке есть перп** (двоеточие в имени), а не
  только перп-веткам. Спотовая стратегия может держать перп как источник сигнала, не
  торгуя его: кросс-моментум так смотрит на ставку, чтобы понять фазу рынка. Из торгуемой
  вселенной и из расчёта ширины перпы при этом исключены. История ставок берётся из
  архива (`FundingArchive`) — у REST конечная глубина, ровно 3000 ставок, то есть с конца
  2023 года, и на ней не проверить ни одной гипотезы про 2020–2021.
- **Маржа считается ПО НОГЕ, и ликвидация останавливает стратегию.** У ноги с двоеточием
  в имени (перп или срочный контракт) есть залог — `notional / leverage` из параметров
  карточки; у спота залога нет вовсе. Проверка идёт по ХУДШЕЙ цене бара: биржа смотрит на
  цену непрерывно, и шорт, переживший час «в среднем», мог не пережить его максимум.
  Почему по ноге, а не по стратегии: на бирже спот и фьючерс — разные счета, и шорт
  ликвидируют, даже когда спот-нога того же хеджа в прибыли. Именно так кэш-энд-керри
  из «первой прошедшей порог» превратился в «−2.38% годовых»: 08.05.2021 шорт ETH,
  открытый по 1956, ликвидирован по 3966, а спот в тот момент был **+51%**. Модель грубая
  (изолированная маржа, без страхового фонда, частичных ликвидаций и ступеней плеча) —
  она отвечает «дожил ли счёт», а не «сколько списала бы биржа».
- **Карточка без `stop_loss_pct` получает `StopSpec(max_dd_pct=25)` по умолчанию**
  (`manifest_from_card`). Это не «стоп 2%» из текста карточки: `initial_stop_pct` — стоп на
  сделку внутри правил стратегии, а `StopSpec` — стоп всей стратегии. Просадка 24.9% у
  `trailing-breakout-bot` упёрлась именно в умолчание, а не в параметр карточки.
- **Фандинг берётся из истории, а не из константы.** `FundingStore`
  (`data/funding/venue=…/instrument=…/YYYY-MM.parquet`) плюс `lab data funding --venue …`;
  `PaperEngine` берёт ставку КАЖДОЙ выплаты, а при её отсутствии откатывается на
  `funding_rate` из параметров и считает такие случаи (`funding_missed`). Разница не
  косметическая: на начало 2024 года реальная ставка BTC была 0.037% за 8 часов (≈41%
  годовых), а константа по умолчанию — 0.01% (≈11%), вчетверо меньше. Ставки входят
  в `data_hash`: иначе замер на истории и замер на константе давали бы один отпечаток,
  и вернулся бы сохранённый снимок с чужими цифрами. У спота фандинга нет — история
  читается только для перп-веток.
- **Замер ведёт ПОРТФЕЛЬ инструментов** (движок на каждый, сигнал уходит движку своего;
  капитал и стоп общие на стратегию). Ряды сливаются по времени, кусок делится между ними,
  непрерывность проверяется по каждому отдельно. Стратегия обязана держать состояние
  **по инструментам**: у черепах общая история сложила BTC по 60 тысяч с XRP по полдоллара,
  канал Дончиана считался по каше — портфельный прогон дал ноль сделок там, где на одном
  инструменте их 91.
- **В связке из двух ног любая ПОШТУЧНАЯ обработка врёт — и врёт правдоподобно.** Три
  разных дефекта одной природы за одну сессию: (1) базис считался между ценами разных
  часов — 156 ложных выходов; (2) кривая просадки обновляла пик после каждой ноги —
  фантомные 20% у дельта-нейтральной связки, где итог пары был пара сотен долларов;
  (3) стоп получал сделки по БАРАМ, а метрика группировала по времени закрытия — снимок
  печатал «просадка 0%» и «стоп сработал по просадке» разом. Правило: ноги сравнивать,
  складывать и отдавать стопу **по одному моменту**, а не по одному бару и не по одной
  сделке. Ноги связки приходят разными барами того же часа — это нормальный порядок вещей.
- **После починки в слое данных проверять надо ДАННЫЕ, а не код.** Дефект имени срочного
  контракта (`BTC/USDT:USDT-260925` качался как бессрочный) был найден и исправлен, но
  сборщик запущен на старом образе — и 48 «квартальных» рядов оказались копиями перпа.
  Признак был в цифрах: премия 0.02% годовых там, где по рынку 11%. Проверка — сравнить
  ряды напрямую (`s.read(перп) == s.read(контракт)`), а не смотреть на правдоподобность.
- **Вселенную для кросс-секционных правил нельзя брать у живой биржи.** `fetch_tickers`
  отдаёт только то, что торгуется СЕГОДНЯ: LUNA, FTT и SRM в списке нет, хотя перед
  обнулением они были в топе по обороту. Стратегия «покупать лучших по доходности» на таком
  списке покупает только выживших и показывает прибыль всегда. Источник — каталог архивов
  `data.binance.vision` (`scripts/backfill_universe.py`): 735 пар к USDT против 674 живых,
  мёртвые внутри. Смещение уменьшено, но **не устранено**: архивы делистнутых пар Binance
  со временем удаляет, и до 2020 года выживших в списке больше, чем было на самом деле.
- **Бюджет памяти в замере — общий на все ряды, а не на каждый.** `heapq.merge` заводит все
  потоки сразу, и каждый тянет свой первый кусок: нижний предел в 2 000 баров на инструмент
  безопасен для полусотни рядов и убийственен для 647 — 1.3 млн свечей и SIGKILL по
  `mem_limit` (код 137, вывода нет вовсе). Считает `runner.chunk_for(n)`, предел
  `MIN_CHUNK_BARS = 250`. Признак промаха тот же, что и раньше: пустой вывод `measure run`.
- **На портфеле разрыв в одном ряду не отменяет замер, но обязан попасть в снимок.**
  Во вселенной из сотен пар остановка торгов хотя бы одной есть всегда (COCOS/USDT, январь
  2021), и `IncompleteData` на ней обнулял бы работу целиком. `simulate(allow_gaps=True)`
  (включается бегунком, когда инструментов больше одного) считает пропуски по рядам и барам
  → `Metrics.data_gaps` → строка «ДЫРЫ в данных» в `measure show`. **На одном инструменте
  разрыв по-прежнему делает замер `incomplete`** — там пропуск означает торговлю по
  устаревшей цене, а не «пара не торговалась».
- **Ноги связки приходят РАЗНЫМИ барами — сравнивать их цены «как есть» нельзя.** Ряды
  сливаются по времени, но каждый бар всё равно один: на баре спота цена перпа в состоянии
  стратегии ещё с прошлого часа. Их разность — не базис, а движение рынка за час, и на
  волатильном часе она сама уходит за порог. Фандинг-арбитраж на этом закрылся 156 раз из
  156 «по базису» при настоящем базисе BTC не глубже −0.04% и пороге −1%; замер показал
  −6.65%, хотя правило по фандингу отрабатывало верно и даёт +1.09%. Отказ **тихий и
  правдоподобный**: цифры выходят разумные, таблица издержек убедительная, вывод неверный.
  Правило: у каждой ноги хранить ВРЕМЯ её бара и считать спред только при совпадении
  (`_Pair.spot_ts/perp_ts` в `strategies/neutral.py`). Касается всего, что сравнивает два
  ряда: базис, кросс-моментум, парная торговля.
- **Причина каждого выхода пишется в снимок (`Metrics.reasons`) — без неё поведение
  стратегии не разобрать.** `inputs` уходит в `inputs_hash`, а хеш обратно не читается,
  поэтому «почему закрылись» узнать было негде. Строка `причины сделок` в `measure show`
  за один прогон объяснила и ранний стоп черепах, и баг с базисом выше. Если добавляешь
  правило выхода — клади `reason` в `inputs`, `Strategy.signal` перенесёт его в `meta`.
- **Стоп умеет «вылечить» стратегию в глазах порога.** Черепахи в четверть размера порог
  прошли тем, что стоп сработал через десять месяцев: дальше 339 сигналов отброшено, три
  года простоя, просадка мала, EV положительный — все критерии довольны, а торговли нет.
  Поэтому **вердикт одиночного окна нельзя читать без строки о стопе**, а ловится это
  устойчивостью: в скользящих окнах стоп считается заново, и там вышло 3 окна из 8 (38%)
  при требуемых 60%. Разбор — `docs/research/measurements-2026-09-07.md`.
- **Судить стратегию по одному окну нельзя: у биткоина сменился режим.** Среднегодовой рост
  BTC по двухлетним окнам: +1622% в 2011–2013 и +3% в 2024–2026 — разброс в три порядка.
  Ранняя капитализация не повторится, поэтому «обогнать BTC» на окне 2011 года и на окне
  2024-го — разные по сложности требования, а вердикт получается свойством нарезки:
  `pifagor-forever-sma` на пятилетке с 2021 выглядела как edge (+6.8 пункта), на 15 годах —
  как разгром. Правильный инструмент — `lab measure rolling` (окна + доля окон, где
  стратегия впереди): у той же стратегии 5 окон из 26, то есть преимущества нет.
- **Порог смотрит на устойчивость, а не только на одно окно.** `Metrics.stability`
  (`windows/profitable/ahead/compared`) даёт два критерия: `stability_profitable`
  (в скольких окнах стратегия в плюсе после издержек) и `stability_vs_benchmark`
  (в скольких обошла бенчмарк). Настройки — `config/threshold.yaml`, раздел `stability`.
  Оценки нет — критерии просто не добавляются, порог работает как раньше по одному окну.
  Считает `ops.measure.run_stability` (он же за командой `lab measure rolling`), а в
  воскресном переизмерении она запускается **только** для стратегий, прошедших остальные
  критерии: прогон по окнам стоит десятков замеров.
- **Бенчмарк — свой у каждой ветки, а не BTC на всех** (`config/threshold.yaml`, раздел
  `benchmark`): споту `btc_dca` (равные докупки раз в месяц), перпам, мемам, NFT и
  предсказаниям `cash` («не делать ничего»), копитрейдингу `btc_bh`. Единый BTC отбраковывал
  стратегии, ценные в боковике и падении, — то есть ровно то, ради чего система строится.
  DCA вместо «купил разом» потому, что результат входа одной суммой зависит от даты входа:
  у `pifagor-forever-sma` на окне с 10.2021 против lump-sum выходило +26.5 пункта, против
  докупок — −1.9, и вся разница в том, что вход пришёлся на вершину. Вид бенчмарка пишется
  в снимок (`benchmark_kind`) — без него «обошла бенчмарк» нечитаемо.
- **Окна размечаются по фазе рынка** (рост / боковик / падение по годовому росту BTC,
  границы ±15% в `ops.measure.market_phase`), `lab measure rolling` печатает разбивку.
  Вопрос «работает ли стратегия в своей фазе» важнее, чем «обогнала ли биткоин вообще».
- **Сравнение с бенчмарком считается в годовых** (`cagr_pct`, `btc_cagr_pct`, `vs_btc_cagr`),
  потому что разница процентов за окно на длинной истории нечитаема (−2 852 951). На окне
  короче нескольких недель годовые не считаются вовсе — растянуть двое суток на год даёт
  10^39 %, чего не принимает даже `Decimal`, — и критерий откатывается на проценты за окно.
  **Вердикт от единицы не зависит:** годовые монотонны по доходности за то же окно.
  Разбор — `docs/research/measurements-2026-09-07.md`.
- **Длинную историю даёт только Bitstamp: BTC/USD с 18.08.2011.** У Binance BTC с 2017,
  у Bybit с 2020, Kraken отдаёт лишь два последних года. Площадка заведена ТОЛЬКО как
  источник данных: в `VENUES` (регистрация торговых исполнителей) её нет, ключей нет,
  тариф в `costs.yaml` — 40/25 bps, дороже реальных бирж намеренно. Копия стратегии на
  другом ряду заводится `scripts/register_coded_strategy.py --venue --instrument
  --slug-suffix`; ссылка на исходные правила остаётся в `params["code_id"]`.
- **Короткое окно замера даёт ложный вердикт — и это не теория.** `cex-spot-preset-3commas-dca-safety`
  на окне 45 суток числилась провалившей порог, на 400 сутках прошла его: 37 сделок,
  Sharpe 2.24, против BTC +30.8%. Окно короче нескольких месяцев показывает одно настроение
  рынка и ничего не доказывает — ни «плохая», ни «хорошая». Если окно пришлось урезать
  ради ресурсов, вердикт считать черновым и перемерять, а не заносить в выводы.
  Отдельно про смысл цифр: та же стратегия дала **+0.09%** за 13 месяцев, а порог прошла
  потому, что BTC за окно упал. «Обошла бенчмарк» и «заработала» — разные утверждения.
- **Замер читает свечи потоком (было: держал окно целиком).** До правки `measure run` на 1m
  за 400 суток занимал ~2.1 ГБ (ряд стратегии плюс такой же ряд бенчмарка) и получал SIGKILL:
  команда завершалась **молча**, код 137, в базе ни строки. Теперь источник спрашивается
  кусками по `CHUNK_BARS`, отпечаток считается на лету, бенчмарк берётся краями окна —
  тот же замер занимает 283 МиБ. Пустой вывод `measure run` по-прежнему означает OOM,
  а не «нечего считать»: проверять `dmesg -T | grep -i "killed process"`. Контейнерам
  выставлен `mem_limit`, чтобы промах убивал только лабораторию: без него жертву выбирает
  ядро по всей машине, а рядом живут `crypto-trader`, `wake` и `smart-money`.
- **Инструменты в карточках пресетов должны называться по-ccxt.** `BTCUSDT-PERP` из
  карточек `cex-perp-*` фид не понимает: `bybit does not have market symbol BTCUSDT-PERP`,
  замер уходит в `incomplete`. Правильно — `BTC/USDT:USDT` (перп) и `BTC/USDT` (спот).
- **Два «registry» и два «ladder».** `strategies.registry` ≠ `core.registry`;
  `core.ladder` (ступени) ≠ `strategies.meme.ladder` (лесенка продаж). Смотри импорт.

## Что не доделано

- **Живая торговля не проверялась ни на одной площадке.** Всё исполнение прогонялось
  в `paper` и на фейковых транспортах; ни один реальный ордер не отправлялся.
- **Подпись live-транзакций в сетях и на Polymarket не написана** — см. грабли выше.
  Работает только чтение и бумага.
- **Разборщики ончейн-ответов написаны по документации**, а не по живым ответам:
  Helius SWAP, Etherscan V2, tonapi, Hyperliquid `userFills`, Polymarket Data API,
  лидерборд HL (неофициальный хост). Первый живой запуск, скорее всего, потребует
  правок в разборе.
- **Индикаторы Pifagor и Coinmetrika — версии v0 по публичным описаниям.** Pine-кода нет
  ни у одного (профиль TradingView `Pifagor_trade` — 0 скриптов; Coinmetrika — закрытая
  подписка). Закодировано только то, у чего явная база (MFI, SMA, RSI-4w и три «старших»
  индикатора); остальные — заглушки `[ИНДИКАТОР — нужен скрипт]`. Эталон для v1 — даты
  сигналов со скриншотов пользователя на BTC 1W/1M, ряд с 2012 (Bitstamp), не Binance.
- **Индекс внимания NFT: `mentions_growth` без источника упоминаний.** `MentionsSource` —
  протокол, реализации нет; веса индекса — гипотеза и сами предмет замера (`hypothesis=True`).
- **Бенчмарк «кэш» считается нулём и потому льстит нейтральным стратегиям.** Фандинг-арбитраж
  с +0.45% годовых формально «обошёл бенчмарк», хотя те же деньги в казначейских бумагах
  дали бы 4–5%. Честная планка для `cash` — безрисковая ставка за окно, а не ноль; пока её
  нет, вердикт «обошла бенчмарк» у веток с `cash` читать как «не хуже, чем ничего».
- **`ops.portfolio.LivePortfolio` на живых балансах не гонялся** — цифры собираются из
  исполнителей и журнала, проверено только на фейках.
- `events()` у всех фидов — опрос REST, не WebSocket. Отдельной таблицы фандинга нет:
  платежи ложатся в журнал через `Costs(funding=...)` (`ops.funding`).
- Ветка `rh`: акции исполнению не подлежат вообще — `SignalOnly`, ступень `signal`
  навсегда, исполняет оператор руками и отмечает кнопкой в боте.

## `.env` на машине и на сервере — разные файлы, и расходятся молча

Ключи заводятся локально, а лаборатория работает на сервере. 14.09.2026 выяснилось,
что `DUNE_API_KEY` заполнен только локально: для лаборатории его не существовало,
и понять это по поведению нельзя — источник просто спит. Перенос — `scripts/env_sync.py`
(файл→файл, печатает только имена, по умолчанию сухой прогон, цель копируется в бэкап).

**Проверка «непусто» лжёт.** В `.env.example` у каждой строки пояснение, и после
`cp .env.example .env` строка `TELEGRAM_API_ID=  # получить на my.telegram.org` выглядит
заполненной для наивного `grep`. Так я дважды объявил ключи Telegram имеющимися, хотя
их не было вовсе. Проверять надо ЗНАЧЕНИЕ после `_strip_comment`, а лучше — вызовом
к API: у Dune настоящий ключ даёт 200, неверный — 401 «invalid API Key».

Смежное: у ключа есть ОЖИДАЕМАЯ форма, и она ловит подмену. `TELEGRAM_API_ID` — целое
число из 7–8 цифр; значение в 44 символа без единой цифры ключом быть не может.

## У правила из нескольких ног обязателен ПЛАЦЕБО-тест на каждую ногу

Ротация золото/BTC — первая стратегия лаборатории, прошедшая устойчивость (в плюсе
7 окон из 9, впереди бенчмарка 5 из 9; +39.52% годовых против +13.54% у докупки BTC
при просадке 25.2% против 76.6% у самого биткойна). Но замер сам по себе не говорит,
КАКАЯ нога работает, а без этого стратегию нельзя ни упростить, ни перенести.

Два контроля, оба обязательны и оба дешёвые:

* **убрать ногу** — «только BTC и кэш» даёт +50.9% из +61.6%. Значит доходность делает
  трендовый выход, а не золото, и называть правило «золотым» было бы неправдой;
* **подменить ногу** — поставить вместо золота ETH, BNB, XRP. Доходность может даже
  вырасти (BNB +62.2%), но просадка скачет с −34% до −65…−79%. Отсюда настоящая роль
  золота: не доход, а риск. Причина причинная — когда BTC ломается, крипта ломается
  вместе с ним, убежища внутри крипты не существует.

Смежное: **лимит просадки группы `cex` в 5% неприменим к правилам РАЗМЕЩЕНИЯ.** Это уже
второй случай (первым была накопительная лестница с её 83.6%). Правило, держащее 100%
в активе, наследует просадку актива, и 5% отбраковывают его автоматически. Подгонять
лимит под полученный результат нельзя — это ровно та подмена цели, за которую мы бракуем
чужие исследования; лимиты ярусов размещения должен объявить владелец ЗАРАНЕЕ.

## Тариф источника проверять ВЫЗОВОМ, а не по странице цен

14.09.2026 я просил владельца зарегистрировать три платформы «с щедрым бесплатным
тарифом». Проверка живыми запросами оставила от списка одну: у **Coinglass**
бесплатного тарифа нет вовсе (от $29/мес), у **Glassnode** API нет даже на платном
младшем ($49), а **Santiment** отвечает вообще **без регистрации**. Страница тарифов
и поведение API — разные вещи.

Два признака, которые стоит проверять сразу:

* **глубина истории важнее списка метрик.** У CryptoQuant бесплатный ключ рабочий
  (настоящий даёт 403, неверный — 401), но окно ровно 30 суток, и `from=20240101`
  отвечает `400 Out of allowed request range`. На истории таким ключом не проверить
  ничего — только собирать вперёд, по дню за день.
* **самое ценное часто вообще без ключа.** Coin Metrics Community отдаёт **MVRV
  по BTC с 2010 года, 5902 суток**, без регистрации — глубже, чем платный Glassnode.
  Так же бесплатны Deribit (DVOL, опционы), alternative.me (индекс страха с 2018),
  blockchain.info (с 2009), BitMEX (фандинг с 2016 — глубже, чем архив Binance).

Разбор целиком — `docs/research/free-data-audit-2026-09-14.md`.

## `docker compose exec -T` съедает скрипт, поданный через stdin

`ssh сервер 'bash -s' < script.sh` — правильный способ доставить скрипт с кириллицей
(heredoc её ломает). Но `docker compose exec -T` читает stdin, то есть **остаток
скрипта**, и выполнение обрывается на этой строке БЕЗ ошибки: видно только то, что
успело напечататься до неё. Лечится `</dev/null` у каждого `exec`.

## Чужие правила: проверять ВСЮ сетку параметров, а не объявленный оптимум

Автор публикует лучшее окно из десяти — это отбор по известному исходу. У ротации
«золото против биткойна» сетка показала 4 нед → 56.7%, **8 нед → 73.9%**, 12 нед → 38.5%:
пик ровно там, где авторы объявили оптимум. Настоящее преимущество даёт ПЛАТО,
а не пик; проверка — составной сигнал (голосование соседних окон). Здесь он устоял
(61.5% против 48.0% у BTC на трёх разных стартах) и, как и положено, оказался хуже
лучшего одиночного окна.

Смежное: **выходить в слабость можно, продавать в силу нельзя.** Накопительная лестница
проиграла докупке, потому что продавала в рост; трендовая ротация обгоняет биткойн,
потому что уходит из него, когда тренд сломался. Одно и то же действие — продажа —
с противоположным знаком результата.

## Накопление: продавать в рост дороже, чем ждать скидку

Лестница «откуп у дна, распределение у пика» на BTC с 2011 года дала +13.43% годовых
против +60.38% у простой ежемесячной докупки. Отключение ПРОДАЖ подняло её до +44.78% —
то есть продажи в рост стоят тридцати пунктов годовых. Покупка на просадках сама
по себе докупку не обгоняет (−0.92 на свежем окне): ждать скидки в 20% к годовой средней
значит сидеть в деньгах, пока актив растёт, и простой капитала дороже скидки.

**Ежемесячная докупка — сильный соперник, и пока её никто не обошёл.**

Отдельно: **накопительному ярусу нужны свои лимиты просадки.** У «только покупок»
просадка 83.6% — это просадка биткойна, а не дефект правила; лимит группы `cex` в 5%
построен для торговых стратегий и проваливает любое накопление автоматически.

## Фильтр фазы: проверять ТОЛЬКО по прошлому

Разметка фазы «за то же окно, что и сделка» — это будущее, и на ней любой фильтр выглядит
блестяще. У шорта листингов разрыв между падением и ростом был **23.1 пункта** на такой
разметке и **4.1 при шуме около десяти** на причинной (ход BTC за 30 дней ДО входа).
Фильтры фазы в лаборатории провалились четырежды; теперь понятно, почему они так
соблазнительны.

Побочно: если стратегия работает во всех фазах примерно одинаково — это ЛУЧШЕ, чем
«работает в падении»: не нужен ни фильтр, ни угадывание режима.

## Правка карточки НЕ доходит до замера сама

`strategies.registry.build` накладывает параметры записи реестра ПОВЕРХ карточки
(`{**base.params, **params}`), а `--update` параметры намеренно не трогает. Значит после
правки карточки замер молча идёт по СТАРЫМ правилам, и понять это можно только по числам,
совпадающим до последней цифры.

Поймано на стратегии листингов: стоп и размер позиции правились в карточке трижды,
а в записи оставались исходные. Лечится явным ключом:
`register_coded_strategy.py --sync-params`.

Рядом: **пересобирать образ только через `bash deploy/update.sh`.** Ручной
`up -d --build` не проставляет `LAB_CODE_VERSION`, снимок замера получает
`код unknown`, и кэш замеров перестаёт различать версии кода.

## Интервал фандинга принадлежит инструменту, а не площадке

У Binance BTC и ETH платят фандинг раз в восемь часов, **альты — сплошь раз в четыре**.
Движок брал интервал из конфига по ПЛОЩАДКЕ и начислял альтам половину выплат.
Поймано косвенно: замер фандинга листингов насчитал 180 выплат за 30 дней вместо 90.
Теперь интервал выводится из истории ставок, конфиг — запасной путь.

Перемер B1 после этого и после ревизии: +2.84% → **+2.07% годовых при просадке 5.38%**,
вердикт `failed` по двум критериям.

## Ревизия измерителя 12.09.2026: что было сломано

Полный разбор — `docs/research/audit-2026-09-12.md`. Коротко, чтобы не наступить снова:

- **`max_dd_pct: 0` у стратегии, которая держит позицию, — это сломанный измеритель,
  а не хороший результат.** Просадка считалась только по ЗАКРЫТЫМ сделкам: позиция,
  просевшая на 40% и закрытая в +1%, просадки не давала, а открытая на конец окна
  выпадала из итога. Теперь симулятор переоценивает позицию по цене бара, `max_dd_pct` —
  худшая из двух. Кэш-энд-керри после этого: 0% → **9.31%** при лимите 5%, вердикт
  `passed` → **`failed`**. Принятых стратегий у лаборатории на сегодня нет.
- **Перекрывающиеся окна — не независимые наблюдения.** 730 дней с шагом 180: «8 окон
  из 8» — это ≈2 независимых. Число печатается в критерии устойчивости.
- **Все найденные изъяны смещали результат в одну сторону** — в пользу стратегии.
  Поэтому отвергнутые гипотезы остаются отвергнутыми с запасом, а перепроверять надо
  только принятые.

## Порядок проверки гипотезы (выведен 11–12.09.2026, соблюдать)

Стратегия пишется ПОСЛЕДНЕЙ. Правило на вымывании плеча писалось, кодировалось,
регистрировалось и мерилось — и дало `insufficient` на восемнадцати сделках, то есть
не ответило ничего; прямая проверка того же заняла минуту и показала, что эффекта нет.

1. **Есть ли эффект** — `scripts/signal_check.py`: доходность вперёд у хвостов показателя
   против ОБЫЧНОГО дня (у рынка свой дрейф, и «+1% за пять дней» без этого сравнения
   ничего не значит).
2. **Не сводится ли к более простому** — контроль по цене: сравнивать дни с ОДИНАКОВЫМ
   движением. Поток тейкеров эту проверку прошёл (внутри равных падений разделяет исходы
   в 13 раз), а «вымывание плеча» — нет.
3. **Переживает ли реалистичный вход** — доходность от СЛЕДУЮЩЕГО открытия, а не от
   закрытия дня сигнала.
4. **Устойчив ли по ГОДАМ.** Согласованность по инструментам ничего не доказывает: пять
   монет ходят вместе, и пять подтверждений — это одно, повторённое пятикратно. Поток
   тейкеров прошёл проверки 1–3 и по всем пяти инструментам, а по годам развалился:
   весь плюс дали бычьи 2023–2024, в падающие он теряет больше обычного дня.
5. Только теперь — карточка, правила, издержки, стоп и замер.

**Шум считается по независимым моментам времени, а не по строкам таблицы.** Восемь монет
в один день — одно наблюдение. Разница между «по барам» и «по датам» не в точности,
а в ОТВЕТЕ: у часового эффекта фандинга при пересчёте по датам перевернулся знак, а эффект
экспирации опционов (−0.42 п.п., вчетверо больше круга по тейкеру) оказался вдвое уже
собственного коридора ±0.89. По средним это была находка; по шуму — ничего.

Отсюда два порога подряд, и оба обязательны: разница больше собственного шума (2σ)
**и** больше круга по издержкам (≈0.04% по мейкеру, ≈0.10% по тейкеру на перпах Binance).
Считают сами: `scripts/calendar_effects.py`, `scripts/xsection_check.py`.

**Правило переноса чужой стратегии:** эффект живёт, только если его причина больше
издержек того, кто должен на неё отреагировать. Лонги не выходят перед расчётом фандинга,
потому что ставка 0.01% за восемь часов меньше комиссии 0.05% за круг — мотивации нет
физически. Календарные эффекты в акциях жили при комиссиях в десять раз выше и при
закрытии рынка на ночь; оба условия ушли.

**Кросс-секция: два обязательных контроля.** (1) Фильтр торгуемости — без порога оборота
в крайние десятые части попадает именно то, что нельзя купить: первый прогон дал вселенную
«+38.61% за месяц» и дециль «+6122%» на свежих листингах с микроскопической первой ценой.
(2) **Ориентир BTC в каждом замере.** Любой длинный портфель в крипте — ставка на биткойн
