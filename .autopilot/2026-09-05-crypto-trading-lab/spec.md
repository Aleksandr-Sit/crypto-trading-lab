# Спецификация: crypto-trading-lab

Режим: интервью · глубина: максимальная. Источники: `2026-09-05-brief.md`, ответы В1–В25, `premortem.md`, `research-sources.md`.

## Задача

Я торгую криптой руками и по наитию, у меня много кошельков и аккаунтов на биржах, и я вижу вокруг сотни «стратегий» — от индикаторов известных трейдеров до сигнальных каналов, ботов и кошельков, за которыми стоит следовать. Я не знаю, какие из них реально работают на моих деньгах после комиссий, а какие — красивая витрина. Я не хочу верить и не хочу спорить. Я хочу, чтобы всё это было измерено одним и тем же способом, и чтобы система сама сказала: вот это прошло замер, вот это нет, вот это ещё меряется. И чтобы это не разваливалось через две недели, когда кончится бесплатный тир или протухнет ключ.

## Решение

Одна система на моём VPS, в которую я кладу гипотезу — стратегию, кошелёк, канал, индикатор, коллекцию — и она проходит одну и ту же дорогу: **бэктест (если возможно) → бумага → микро-деньги → сигнал в телегу → подтверждение кнопкой → автомат**. Каждая ступень требует пройти статистический порог после издержек; ступень вниз — автоматически, ступень вверх в автомат — только моей рукой. Раз в неделю система сама ищет новых кандидатов, переизмеряет старых и предлагает перелить прибыль из рискованных веток в спокойные. Утром в 9:00 я получаю в телегу одну картину: что сделано за ночь, что прошло порог, что упало, что ждёт моего решения. В браузере — второй экран, для сравнения стратегий между собой. Ветки: спот и перпы на CEX и Hyperliquid, копитрейдинг кошельков и трейдеров, мем-коины в Solana/EVM/BNB/TON, NFT с ранним входом и минт-снайпингом, Polymarket, Robinhood. Ни одна из них не отвергается на теории — каждая получает свою строку в реестре и свои цифры.

## Словарь

| Термин | Значение |
|---|---|
| **Ветка** (branch) | Класс рынка со своими лимитами: `cex-spot`, `cex-perp`, `dex-perp` (первый — Hyperliquid; другие DEX-перпы — по флагу, G07-порядок), `copy`, `meme`, `nft`, `prediction`, `rh` |
| **Стратегия** | Запись реестра: правила + параметры + площадка + ветка + ступень + статус. Единица замера |
| **Кандидат** | Стратегия до первого замера, в очереди |
| **Ступень** (rung) | `backtest` → `paper` → `micro` → `signal` → `semi` → `auto` (В8, В12) |
| **Статус** | `candidate` · `measuring` · `passed` · `failed` · `degraded` · `retired` |
| **Замер** | Один прогон стратегии на одном режиме (бэктест / бумага / микро / форвард) с итоговым набором метрик |
| **Порог** | Правило В12: ≥30 сделок, EV>0 после издержек, MaxDD в лимите, лучше BTC B&H за период |
| **Издержки** | Комиссия + проскальзывание + фандинг + газ + приоритетные fee + спред. Всегда считаются, никогда не «потом» |
| **Сигнал** | Намерение стратегии открыть/закрыть позицию до того, как оно стало ордером |
| **Исполнитель** (executor) | Коннектор площадки, умеющий `place / cancel / positions / fills` в режимах paper и live |
| **Источник** (feed) | Поставщик данных с health-check и квотой |
| **Экран оператора** | Утренний отчёт + карточки с кнопками в Telegram |
| **Экран исследователя** | Веб-дашборд для сравнения и разбора |

## Решения по реализации

1. **Язык и рантайм — Python 3.12, `uv`, один репозиторий, четыре процесса в docker-compose: `db` (Postgres 16), `worker` (планировщик, фиды, замеры, исполнение), `bot` (Telegram, aiogram 3), `web` (FastAPI + Jinja + HTMX, без JS-сборки).** Почему: пользователь работает в Python-проектах (crypto-trader, solana-smart-money), все коннекторы — Python, VPS один и небольшой; фронтенд без сборки — чтобы обслуживать одному.
2. **Хранение: Postgres для оперативного состояния (реестр, сигналы, ордера, сделки, замеры, очередь), Parquet-файлы по месяцам для свечей/сделок рынка, читаются DuckDB.** Почему: свечи за год по сотням инструментов дёшевы в Parquet и дороги в строках Postgres; оперативное — транзакционно.
3. **Бэктест: собственный событийный симулятор с моделью издержек + `vectorbt` OSS для быстрого перебора параметров правил на свечах.** Почему: чужие фреймворки не знают наших ступеней, издержек по площадкам и форвард-журнала; vectorbt даёт скорость там, где правила векторизуются.
4. **Модель издержек — по площадке, версионируемая: taker/maker fee по тарифу, проскальзывание = f(размер / глубина стакана или ликвидность пула), фандинг по факту, газ + приоритет по факту/оценке, роялти для NFT.** Почему: P1 из премортема — издержки убивают эджи, значит считаются с первого дня.
5. **Коннекторы: `ccxt` для Bybit/OKX/Binance/Hyperliquid (единый контракт), `hyperliquid-python-sdk` для HL-специфики (лидерборд, userFills), `solana-py`+`solders`+Jupiter API для Solana, `web3.py`+агрегаторы для EVM/BNB, `tonapi`+STON.fi для TON, `py-clob-client` для Polymarket, официальный Robinhood Crypto API, Magic Eden/OpenSea/Zora REST для NFT, Tensor — при получении ключа.** Почему: проверено в `research-sources.md` на 09.2026.
6. **Каждый коннектор реализует два контракта: `Feed` (данные) и, если площадка торгуется, `Executor` (ордера) с режимами `paper` и `live`; `paper` использует те же котировки и модель издержек.** Почему: замер бумаги и реальности должен идти по одному коду, иначе разница между ними — артефакт кода, а не рынка.
7. **Лестница — конечный автомат в ядре, не в стратегиях.** Переходы вверх вычисляются планировщиком по порогу; `semi→auto` только командой; вниз — автоматически по порогу/стопу. Стратегия не может изменить свою ступень.
8. **Риск-ядро — одна функция `check(order) -> allow | deny(reason)` перед каждым ордером, проверяет: лимит ветки, стоп стратегии, размер от текущего капитала, плечо, ликвидацию, доступность площадки.** Обойти нельзя: исполнители не принимают ордер без подписи риск-ядра.
9. **Стратегия — Python-класс с декларативным манифестом (ветка, площадка, инструменты, параметры, `can_backtest`, стоп) и методами `on_bar`/`on_event` → сигналы.** Копитрейд, мемы, NFT, Polymarket — те же классы с другими событиями. Внешние проекты — класс `ExternalSignalStrategy`.
10. **Форвард-журнал: любое решение пишется с `decided_at` и хешем входных данных до того, как известен исход.** Почему: P2 — ранние стадии и минты иначе не измеримы честно.
11. **Планировщик — APScheduler в `worker`: тики фидов, еженедельный поиск (пн 06:00), еженедельное переизмерение (вс 22:00), предложение перелива (вс 22:30), утренний отчёт (ежедневно 09:00 Europe/Samara), сверка с площадками (04:00), бэкап (03:00).**
12. **Источники: реестр `feeds` с квотой (лимит/период), счётчиком, health-check, приоритетом и запасным источником.** Бюджетомер суммирует платные.
13. **Секреты — только через `.env` по именам из `.env.example`; система при старте перечисляет, какие заполнены. Ключи с правом вывода отклоняются. Приватные ключи кошельков — отдельные «горячие» кошельки только под тестовый капитал.**
14. **Telegram — существующий бот Trader (токен `TELEGRAM_BOT_TOKEN`), команды только от `TELEGRAM_ADMIN_ID`.** Карточки с inline-кнопками; необратимые действия — двойное подтверждение.
15. **Веб — на VPS, за HTTP Basic (`WEB_USER`/`WEB_PASSWORD`), только по localhost или за VPN/reverse-proxy пользователя.** Один пользователь (G11).
16. **Конфиг — `config/limits.yaml` (раскладка и лимиты веток из В9а), `config/threshold.yaml`, `config/schedule.yaml`; горячая перезагрузка с записью изменений.**
17. **Тесты: контрактный тест исполнителей (один набор на все площадки, в `paper`), тест риск-ядра, тест симулятора на синтетических свечах с известным ответом, тест порога, тест модели издержек.** Живые API в тестах не вызываются.
18. **Идентификаторы стратегий — читаемые: `<ветка>-<источник>-<слаг>`, например `hl-copy-0xabc…`, `meme-sol-pumpfun-early-v1`, `nft-mint-priority-fee-v2`.**

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `core.registry` | таблицы strategies/candidates, статусы | `add(spec) -> Strategy`, `get(id)`, `list(filter)`, `retire(id, reason)`, `enqueue_candidate(kind, ref)` | генерацию id, отпечатки дубликатов |
| `core.ladder` | ступени и переходы | `evaluate(strategy_id) -> Transition|None`, `promote(id, by)`, `demote(id, reason)`, `halt_all()`, `resume_all()` | правило порога, историю переходов |
| `core.risk` | лимиты веток, стопы, раскладку | `check(OrderIntent) -> Allow|Deny(reason)`, `allocation(branch) -> Allocation`, `reload()` | арифметику размера, чтение конфига |
| `core.measure` | замеры, метрики, порог | `run(strategy_id, mode, window) -> Measurement`, `metrics(trades, benchmark) -> Metrics`, `threshold(metrics, branch) -> ThresholdResult` | симулятор, бутстрап, бенчмарк |
| `core.costs` | модели издержек по площадкам | `estimate(venue, intent, book|pool) -> Costs`, `actual(fill) -> Costs` | тарифы, формулы проскальзывания |
| `core.journal` | signals/orders/fills/trades, форвард-журнал, сверка | `record_signal(...)`, `record_fill(...)`, `close_trade(...)`, `reconcile(venue)`, `export_csv(filter)` | связывание филлов в сделки |
| `feeds.*` | данные площадок и сетей | контракт `Feed`: `candles(instr, tf, from, to)`, `trades(...)`, `book(instr)`, `events(kind) -> stream`, `health() -> Health` | клиентов API, ретраи, квоты |
| `executors.*` | ордера на площадках | контракт `Executor`: `place(intent, mode) -> Order`, `cancel(order_id)`, `positions()`, `fills(since)`, `balance()` | подписи, client_order_id, реконнект |
| `strategies.*` | правила | `Strategy.manifest`, `on_bar(bar) -> [Signal]`, `on_event(evt) -> [Signal]` | внутреннее состояние правила |
| `discovery` | поиск кандидатов | `scan() -> [Candidate]` по источникам: OKX lead traders, HL leaderboard, Polymarket leaderboard, смарт-мани фиды, GitHub, ME launchpad | парсеры и дедупликацию |
| `wallets` | статистика кошельков/лидеров | `recalc(address, chain) -> WalletStats`, `flags(address) -> [Flag]`, `lag_cost(address) -> LagCost` | индексацию сделок |
| `nft` | коллекции, создатели, минты | `track(collection)`, `creator_score(creator) -> Score`, `upcoming() -> [Mint]`, `mint(attempt_spec) -> MintResult` | парсинг календарей, специфику площадок |
| `ops.scheduler` | расписание | `register(job)`; сами задания — из других модулей | APScheduler |
| `ops.feeds_registry` | квоты, здоровье, бюджет | `use(feed_id, n)`, `status() -> [FeedStatus]`, `budget() -> Budget` | подсчёт прогноза |
| `bot` | Telegram | `send_card(kind, payload) -> msg_id`, `morning_report()`, команды | aiogram, outbox |
| `web` | HTTP-экраны | маршруты `/`, `/strategies`, `/strategies/{id}`, `/feeds`, `/queue`, `/graveyard` | шаблоны |

**Швы для тестов (три):** `Executor` в режиме `paper` (один контрактный набор на все площадки), `core.risk.check`, `core.measure.run` на синтетических данных. Стратегии тестируются через `core.measure.run`, не напрямую.
