# 0008. Хранение раздельное: Postgres для оперативного состояния, Parquet + DuckDB для рыночных рядов

- Статус: принято
- Дата: 2026-09-07
- Требования: R28i, R28i.1, R05, R05.1, R32i.3; решение §2 спецификации

## Контекст

Данные системы делятся на два несовместимых профиля. Оперативное состояние — реестр,
кандидаты, сигналы, ордера, филлы, сделки, замеры, очередь — небольшое, часто
обновляемое, требует транзакций и уникальности (идемпотентный `client_order_id`,
одна запись на стратегию). Рыночные ряды — свечи и сделки за год по сотням инструментов
из реестра — пишутся пачками, читаются диапазонами и почти не меняются. Решение §2
называет причину: свечи за год по сотням инструментов дёшевы в Parquet и дороги в
строках Postgres, а оперативное состояние должно быть транзакционным. Требование R28i.1
формулирует срок: «через год данных всё ещё работает».

## Решение

Postgres 16 держит оперативное состояние по схеме ядра; изменения — только новой
ревизией alembic, голова одна. Свечи и рыночные сделки лежат в Parquet-файлах,
партиционированных по месяцам, и читаются DuckDB через `CandleStore`. Загрузка
идемпотентна: повторный бэкфилл не плодит дублей, прерванный — продолжается с места
остановки и показывает прогресс. Резервная копия по расписанию берёт и то, и другое
(дамп базы плюс конфиги), восстановление описано отдельным скриптом. Перезапуск
контейнеров ничего не теряет.

## Последствия

Стало легко: год истории читается диапазонными запросами без роста базы и без
партиционирования средствами Postgres; замер воспроизводится по `data_hash` над
неизменяемыми файлами.

Цена: два хранилища — два способа резервного копирования, два места, где состояние
может разъехаться, и запрос, соединяющий сделку из Postgres со свечой из Parquet,
пишется руками, а не одним JOIN. Транзакции через границу нет: файл свечей может
записаться, а запись о замере — нет, и согласованность держится на порядке операций,
а не на базе. Появляется вторая технология в эксплуатации (DuckDB) — ещё одна вещь,
которую обслуживает один человек.
Теперь нельзя: сделать целостный снимок системы одной командой `pg_dump`; положиться
на внешние ключи между рыночными рядами и оперативными таблицами.

## Что рассматривали и отвергли

- **Всё в Postgres.** Свечи строками дают десятки миллионов строк на инструмент-год,
  дорогие диапазонные чтения и раздутый дамп — прямо названо в §2.
- **Всё в файлах.** Реестр, статусы, ордера и очередь требуют транзакций, уникальности
  и одновременного доступа четырёх процессов; файлы этого не дают, а восстановление
  ордеров после рестарта (R16.2) становится ненадёжным.
- **Специализированная time-series-СУБД** (например, расширение Timescale или отдельная
  колоночная база). В источниках такой вариант не обсуждался — причина отказа не
  записана. Решение опирается только на довод §2: Parquet дёшев, оперативное —
  транзакционно; ни цифр сравнения, ни требований по нагрузке в спецификации нет.
