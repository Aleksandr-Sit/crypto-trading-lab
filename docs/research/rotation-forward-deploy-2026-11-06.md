## Порядок после одобрения выкладки

Зафиксированный релиз сначала публикуется в GitHub и доставляется на сервер.
Все долгие операции запускать через `scripts/run-detached.sh`; команды ниже —
содержимое серверной задачи в `/opt/crypto-trading-lab`, а не команда для вставки
в локальную PowerShell. При любой ошибке остановиться и сохранить диагностический лог
без секретов. Не запускать старый worker после применения миграций без разбора причины.

1. Повторить аудит, сверить чистоту дерева сервера и отсутствие отдельного замера.
   Убедиться, что только согласованный коммит станет новым HEAD. Записать текущие
   image id сервисов и текущий коммит для восстановления. Сервисы CryptosMX оставить
   работающими на прежних образах.
2. Обновить checkout до согласованного коммита. Собрать только четыре образа:

   ```bash
   export LAB_CODE_VERSION="$(git rev-parse HEAD)"
   docker compose -f deploy/docker-compose.yml build migrate worker bot web
   ```

   Рабочие контейнеры продолжают работать во время сборки. Конфиги смонтированы
   с хоста: новый минутный job в старом worker до перезапуска не зарегистрирован;
   окно между обновлением файлов и остановкой держать коротким.
3. Остановить только worker/bot/web, чтобы никто не писал при исправлении ступени.
   Создать резервную копию базы и конфигов одноразовой командой образа worker
   (backup не требует новой схемы). Проверить, что архив существует и не пуст.
   Пароль базы не выводить и не передавать в строке команды.
4. Выполнить миграции и предварительную проверку исправления:

   ```bash
   docker compose -f deploy/docker-compose.yml run --rm --no-deps -T migrate
   docker compose -f deploy/docker-compose.yml run --rm --no-deps -T worker \
     uv run python scripts/prepare_rotation_forward.py
   ```

   Ожидается схема 0014 и план `semi → signal → micro → paper`, `applied: false`.
   Скрипт откажет при изменённых параметрах/ступени/статусе, появлении сигналов,
   сделок, контракта наблюдения или состояния сборщика. Чужие стратегии он не меняет.
5. Применить согласованное исправление один раз:

   ```bash
   docker compose -f deploy/docker-compose.yml run --rm --no-deps -T worker \
     uv run python scripts/prepare_rotation_forward.py --apply
   docker compose -f deploy/docker-compose.yml up -d --no-deps worker bot web
   ```

   Три понижения и контракт наблюдения фиксируются одной транзакцией; старые четыре
   повышения остаются в истории. Дата контракта — реальное время этой транзакции,
   дата разогрева сборщика — последующее реальное время. Повторное применение откажет.
6. Дождаться healthy worker/bot/web, сверить `LAB_CODE_VERSION` каждого с релизом,
   проверить регистрацию `virtual_forward` и первый минутный тик. У ротации должно
   появиться состояние сборщика без ошибки; первый тик — только разогрев, без сделок.
   При pending архива наблюдение пока не подтверждает допуск: дождаться сверки.
   Убедиться, что контейнеры CryptosMX сохранили прежние id и время запуска.
7. Повторно сохранить аудит с новой датой, id наблюдения, версией, стартом сборщика
   и состоянием свечей. Обновить отчёт и handoff фактическими результатами.

При сбое миграции/исправления не продолжать запуск. Если сервисы не стали healthy
или сборщик не прошёл разогрев, наблюдение не объявлять начавшим успешный сбор.
Резервную копию восстанавливать только с учётом появившихся после неё записей;
не выполнять автоматическое восстановление или downgrade с удалением данных.

## Критерий готовности

Выкладка завершена только после проверки новой схемы, версий и healthy, трёх
аудируемых понижений, одного нового контракта и первого успешного тика сборщика.
Это начало наблюдения, а не доказательство прибыльности. Итоговый форвард-отчёт
