## По порядку важности

1. `crash_bounce_portfolio.py`: разделены sample_ready и archive_passed.
   Старое ready не даёт разрешения на реальные деньги. Даже legacy JSON с ready=true
   не превращается в положительный вердикт. Выборка с проваленными К1/К2 явно отмечается
   как не прошедшая критерии. Автоматическая проверка К3–К5 добавлена отдельно по исходным
   x1/x25/x5; новые p-счета не подменяют исходный эксперимент.

2. `crash_bounce_paper.py`: свежесть каждого ожидаемого соединения, свежесть обработки
   очереди и проверка времени состояния входят в новый healthcheck. Задержки и качество
   обработки агрегируются, без записи на диск каждой опоздавшей сделки. Поминутные
   битовые маски фиксируют секунды наблюдения и деградации. Отсутствующие секунды
   становятся неизвестным покрытием, а не нулевой слепотой. Даже минута без единого
   сообщения получает диагностическую запись, если процесс продолжает работать.
   Система не останавливает и не меняет виртуальные исполнения замороженного опыта.

3. `crash_bounce_audit.py`: К3 проверяет готовность symbol/day, границу исхода и
   наличие записи до as-of. Пропуски перечислены поштучно: signal_not_recorded или
   outcome_not_recorded; причина считается неустановленной. Есть численная проверка
   объявленных порогов К3, отдельные исключённые события и неполнота архива.
   На текущем журнале: 2038 совпадений из 2095 сравнимых, 57 пропусков, 77 исключений
   из-за дыр. Отличие от старых 2018/2075: исключение дыр ограничено фактическим временем
   жизни позиции, а не полным семиминутным горизонтом после каждого сигнала.
   Все найденные исходы и net совпадают. Эти цифры не устанавливают причину 57 пропусков.

4. Граница минуты: существующая параллельная реализация p-счетов сохранена и проверена
   дополнительными тестами границ, отсутствующего снимка и недопустимости старого уровня.
   Пороговые значения и объявленные счета не изменялись. Само исправление границы уже
   присутствовало с 28.10; повторно заменять им исходные счета нельзя.

5. Стандартный paper report теперь использует t_out для календарной прибыли.
   Период [начало, конец) и момент знания данных as-of разделены: принимаются только
   записи recv < as-of, прибыль относится к t_out внутри периода. Поздний исход после
   конца периода остаётся открытой позицией на его конец. Начальная накопленная прибыль
   и просадка реализованного результата от пика показаны отдельно. Неизвестные
   плавающая прибыль и mark-to-market просадка остаются null, а не нулём.

6. Добавлен стресс дополнительных совокупных издержек входа/выхода: 0/2/5/10/25 б.п.
   Сохраняется набор исполнений, меняется net после дополнительной стоимости.
   Это проверка чувствительности, не модель глубины, очереди и ёмкости.
   На 10.10–08.11 x1p: базовый +3.10% D0, при дополнительных 25 б.п. +1.71% D0.
   Реальные подтверждения постановки/отмены, fills и историческая книга заявок отсутствуют.
   execution_verified остаётся false. Этот пункт выполнен в части доступного анализа,
   реальная исполнимость не подтверждена.

7. Снимки трейдера сохраняются отдельно, обновления сливаются по symbol/positionId.
   Исправление opened не создаёт дубль; старый updateTime и равновременный откат
   закрытой позиции в частичную не затирают актуальную версию. Запись объединённой
   истории атомарная. Есть отдельная сводка покрытия и разделение быстрых Long ×1
   длительностью до 8 минут и прочих сделок. Это описательная группа, а не доказательство
   восстановленного правила. Утилита cryptosmx_history.py сохраняет SHA256 источников,
   не перезаписывает источник и отклоняет датированные снимки новее as-of.

## Использование после выкладки

```bash
python scripts/crash_bounce_paper.py report \
  --out /app/data/crash-bounce-paper --archive /app/data/crash-bounce-forward \
  --from 2026-10-10 --to 2026-11-08 --as-of 2026-11-09T08:24:00Z \
  --json /tmp/cryptosmx-diagnostics.json

python scripts/cryptosmx_history.py SOURCE1.json SOURCE2.json \
  --as-of 2026-11-09T08:26:07Z --out /tmp/cryptosmx-history.json
```

Слой А создаёт execution_diagnostics.json вместе с новым дневным отчётом, если доступен
соседний каталог бумажного журнала. Отсутствие диагностики явно блокирует положительный
вердикт. Прошлые сообщения не переписываются и за уже обработанные сутки не отправляются
повторно. Для проверки прошедших суток использовать read-only CLI.

При будущей выкладке менять образ и Compose согласованно: новая проверка здоровья
зависит от нового кода. Использовать crash-paper-deploy.sh, который ожидает отсутствие
открытых позиций. Не заменять существующий опыт новым запуском и не обнулять журналы.
Объединённая локальная история не импортирована автоматически в боевой том.
